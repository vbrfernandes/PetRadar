=====================================================================
2. OBJETIVO PRINCIPAL
=====================================================================

Ao final da refatoração:

- arquivos .tsx devem concentrar:
  - JSX;
  - props;
  - estado;
  - hooks;
  - callbacks;
  - eventos;
  - comportamento;
  - composição dos componentes;

- arquivos .styles.ts devem concentrar:
  - StyleSheet.create(...);
  - estilos estáticos;
  - estilos específicos de telas;
  - estilos específicos de componentes;
  - agrupamentos visuais por feature;

- o Design System global deve concentrar:
  - cores;
  - espaçamentos;
  - radius;
  - sombras;
  - tipografia/tamanhos reutilizáveis quando aplicável;
  - opacidades/tokens reutilizáveis quando aplicável;

- estilos calculados em runtime podem permanecer no .tsx quando realmente
  dependerem de estado/props/medidas dinâmicas.

Exemplo permitido:

style={[
  styles.progressBar,
  { width: `${progress}%` },
]}

Neste caso:
- progressBar estático vai para .styles.ts;
- width dinâmica pode permanecer no componente.

3. PRINCÍPIOS OBRIGATÓRIOS
=====================================================================

3.1. NÃO FAZER REDESIGN DURANTE A EXTRAÇÃO

A primeira migração deve ser 1:1.

Exemplo:

ANTES:
const styles = StyleSheet.create({
  card: {
    borderRadius: 17,
    padding: 16,
  },
});

DEPOIS:
o mesmo style deve existir no arquivo .styles.ts com exatamente os mesmos
valores.

Não aproveitar a migração para:
- aumentar padding;
- mudar radius;
- mudar fonte;
- mudar cor;
- reposicionar elementos;
- alterar sombras;
- mudar animações.

Uniformização visual deve ocorrer somente depois que a separação estrutural
estiver concluída e validada.


3.2. CÓDIGO REAL É A FONTE DE VERDADE

Antes de cada fase:
- localizar o arquivo real;
- conferir imports;
- conferir exports;
- conferir StyleSheet atual;
- conferir dependências;
- conferir se o arquivo ainda existe.

Não criar arquivos com base apenas neste plano se o código atual já tiver uma
solução equivalente.


3.3. NÃO DUPLICAR STYLES

Se dois componentes realmente reutilizam o mesmo componente visual:
- manter o style na implementação compartilhada;
- não copiar para a feature consumidora.

Exemplo importante:
Procura-se reutiliza componentes do Feed em partes da implementação.
Não criar styles duplicados apenas para ter um arquivo próprio.


3.4. NÃO MISTURAR DESIGN SYSTEM COM LAYOUT DE TELA

Design System responde:
"qual é o padrão visual global?"

Styles da feature respondem:
"como esta tela organiza esse padrão?"

Exemplo:

theme.radius.card
theme.spacing.globalMargin
theme.colors.brand

são globais.

Já:

styles.commentsHeader
styles.mapFloatingButton
styles.petGrid

são específicos da feature/tela.


3.5. NÃO ALTERAR BACKEND

Esta refatoração é exclusivamente frontend/mobile.

Não editar:
backend/
alembic/
routers/
models/
schemas/
services Python/
banco de dados/


3.6. NÃO RENOMEAR theme/colors.ts NESTA REFATORAÇÃO

O arquivo atual:

mobile/src/theme/colors.ts

deve permanecer com este caminho durante este plano.

Motivo:
o projeto possui migrar_design_system.py que procura explicitamente esse
arquivo e gera imports relacionados a theme/colors.

Renomear colors.ts para theme.ts ou index.ts poderá ser feito no futuro em uma
refatoração separada.


3.7. NÃO USAR MIGRAÇÃO AUTOMÁTICA SEM REVISÃO

migrar_design_system.py pode ser usado para:
- auditoria;
- simulação;
- identificação de cores.

Não usar uma alteração em massa automaticamente no meio de uma fase sem:
1. simular;
2. revisar os arquivos afetados;
3. garantir equivalência visual;
4. validar diff.

6. RESPONSABILIDADE DE CADA CAMADA
=====================================================================

6.1. mobile/src/theme/colors.ts

Deve conter tokens globais.

Já possui conceitos como:
- colors;
- shadows;
- spacing;
- radius.

Pode ser complementado com tokens quando isso for necessário para substituir
valores repetidos SEM alterar visual.

Exemplos possíveis:
- typography;
- opacity;
- sizes;
- novos tokens rgba existentes no código.

REGRA:
ao criar um token novo, o valor inicial deve ser exatamente igual ao valor
que já existia no componente.


6.2. mobile/src/styles/shared.styles.ts

Criar apenas se houver styles estruturais realmente reutilizados por features
diferentes.

Exemplos possíveis:
- pressed;
- screenContainer;
- centeredLoading;
- modalBackdrop padrão, SOMENTE se visualmente idêntico.

Não transformar este arquivo em depósito genérico.


6.3. *.styles.ts das features

Devem conter StyleSheet.create e estilos estáticos daquela feature.

Cada export deve ter nome explícito.

Exemplo:

export const loginStyles = StyleSheet.create({...});
export const cadastroUserStyles = StyleSheet.create({...});

ou:

export const occurrenceCardStyles = StyleSheet.create({...});
export const feedControlsStyles = StyleSheet.create({...});

REGRA:

naquele arquivo.

26. COMO LIDAR COM STYLES DINÂMICOS
=====================================================================

ESTILO ESTÁTICO:
deve ir para .styles.ts.

Exemplo:

const styles = StyleSheet.create({
  card: {
    padding: 16,
    borderRadius: 18,
  },
});


ESTILO DINÂMICO:
pode permanecer no .tsx.

Exemplo:

<View
  style={[
    styles.card,
    {
      opacity: disabled ? 0.5 : 1,
    },
  ]}
/>


PREFERÊNCIA:
se a variação dinâmica for recorrente e limitada, criar styles estáticos:

style={[
  styles.card,
  disabled && styles.cardDisabled,
]}

Mas não forçar abstração quando o valor for genuinamente calculado.


=====================================================================
27. COMO LIDAR COM CORES
=====================================================================

ANTES de criar nova cor no theme:
1. procurar token existente;
2. conferir valor exato;
3. conferir significado;
4. reutilizar somente se semanticamente correto.

Não usar:
theme.colors.brand

apenas porque a cor é "parecida".

Se uma cor literal necessária não existir:
- adicionar token com o MESMO valor;
- nomear pelo significado;
- trocar o literal pelo token;
- validar visualmente.

Durante esta refatoração:
preservação é mais importante que uniformização.


=====================================================================
28. COMO LIDAR COM SHARED STYLES
=====================================================================

Um style pode virar shared quando:

1. aparece em mais de uma feature;
2. possui exatamente o mesmo significado;
3. possui exatamente a mesma estrutura;
4. a reutilização reduz duplicação;
5. não cria acoplamento estranho.

Exemplo aceitável:
pressed padrão global, se for realmente o mesmo padrão.

Exemplo ruim:
usar "card" global para:
- card do feed;
- card do pet;
- card de formulário;
apenas porque todos têm borderRadius.
